What this project is, in one paragraph (steal this verbatim)

StateShift is a control plane for moving a live workload from one machine to another. A job is expressed as a state machine; every step commits its effects to an exactly-once op log and its state to a content-addressed checkpoint. To migrate, the source freezes at a step boundary, the checkpoint is transferred as a delta of only the chunks that changed, and an epoch fence in the database hands authority to the target in one atomic statement. The source can no longer commit — provably, not by timeout — so the destination resumes without repeating a single committed effect. We measure the pause and the bytes moved, and we show both on screen while it happens.

02 / the 60-second story

The story the deck tells

Act 1 — the failure everyone has lived through (15 s)

You start a long job. An hour in, the machine reboots, the container is rescheduled, or the spot instance is reclaimed. Everything since the last save is gone. You run it again and pay twice.

Three concrete shapes of this, all true and all easy to say out loud:

  • An LLM agent run. 40 tool calls, $6 of tokens, and the box dies at call 31. Every committed call is already paid for; the restart pays again.
  • A simulation / batch compute. Six hours of progress held in memory. Restarting means six hours.
  • A stateful session. Unpersisted state, open handles, work in flight. There is no "just redeploy it" that does not lose the session.

Act 2 — why the standard answers are not answers (20 s)

Standard answerWhy it misses
Redeploy / restart on the new nodeWorks only for stateless services. Loses in-memory progress and duplicates committed side effects.
Persist everything after each stepThat is durable execution, and it keeps the job pinned to one machine. It does not move it, and it does not survive the machine.
CRIU / transparent process migrationThe real thing, and it needs root, matching kernels, matching environments. In a 24-hour window it either works completely or you demo nothing.
VM live migrationSolves it at the hypervisor layer, which means you own the hypervisor. Not available to an app team.

Act 3 — what we actually built (25 s)

A middle path that is honest, buildable and measurable: migrate the workload's explicit state at step boundaries, with a database-enforced ownership handover so two nodes can never both be authoritative.

03 / problem framing

Problem statement, in the hackathon's own language

The challenge we chose asks for a platform that migrates running workloads between machines. It lists the hard parts explicitly. Here is how the deck should map them — one row per requirement, because judges often grade against the brief's own checklist:

Scope decision — say this out loud, early

We migrate explicit application state, not kernel state. That means no sockets, no file descriptors, no thread stacks. In exchange: no root, no kernel patches, works on any OS, and the failure modes are ordinary software failures instead of "the kernel was compiled without CONFIG_CHECKPOINT_RESTORE".

This is the same trade-off real systems make: Temporal, Restate and Netflix's Conductor all persist application state at step boundaries. We add the part they do not have — the ability to move the running job and measure the move.

Why this problem is worth 24 hours

  • It is hard for the right reasons: semantics, coordination, serialisation, failure handling — not because it needs a big model or a big dataset.
  • It produces numbers, and numbers are what separate a demo from a prototype.
  • It is demoable in one screen: a job counter moving, a button, and the counter continuing on another node.
  • Failure cases are showable, and showing a failed migration adjudicated correctly is more impressive than showing a happy path.

Three roles, one binary

ComponentResponsibilityPackage
WorkerRuns one job at a time per job ID. Commits a step, checkpoints on request, freezes, restores and resumes. Exposes /internal/start, /quiesce, /restore.internal/node

Two design decisions worth a slide

  1. Jobs are never addressable on a node. They exist at /api/jobs/{id} on the coordinator. Consumers hold a logical handle, and the coordinator resolves it to whichever node currently holds the epoch. That is how we answer "network identity" without pretending to move sockets: identities follow the job, not the machine.
  2. The database is the only authority. Not the coordinator's memory, not a heartbeat, not a TTL. If the coordinator crashes mid-migration, the epoch row still names exactly one owner.
deployment rule (put this on the architecture slide as a footnote)
The control plane and the database must not live on either worker. If the database sits on the node you kill during the demo, the demo dies with it.

The eleven steps, in words

#StepWhy it is there
1Coordinator marks the job draining (guarded by status)Intent only. Authority is untouched, so a failure here is free.
2Coordinator calls /internal/quiesce on the ownerThe worker keeps its authority and finishes the step it is in.
3Worker commits that final step, then stops at the boundaryA draining owner is still allowed to commit — otherwise every migration silently loses its last step.
4Worker chunks the state, uploads only missing chunks, writes a manifestThis is the transfer-efficiency claim, and it is measurable.
5Worker inserts a checkpoints row and replies with the sequence numberNow the state is durable somewhere other than the source's memory.
6Coordinator performs the fence: epoch + 1, owner = B, status = restoringThe single point of truth. Must affect exactly one row or the migration aborts.
7Coordinator calls /internal/restore on the target with the manifestTarget pulls only the chunks it needs and reassembles the state.
8Target verifies the reassembled state against the hash the control plane committedBlob and database must agree before anyone runs under a new epoch.
9Target claims the job and flips status to runningOnly now does the new owner begin executing.
10Source observes the epoch changed and exits without side effectsIts next commit would have been rejected anyway; this is the polite version.
11Coordinator computes pause = resumed − quiesced, records the migration rowThe number on the slide is a measured interval, not an estimate.
Pause definition, so nobody argues on stage: from the moment the source freezes at a step boundary to the moment the target begins executing the next step. It includes the checkpoint upload, the fence, the download and the hash verification.
06 / consistency

The epoch fence — the hardest claim in the project

Everything else is engineering. This is the part that is easy to get wrong and impossible to fake. Show the SQL. Judges who know distributed systems will recognise it, and judges who don't will understand "exactly one row can win".

-- ownership handover: exactly one caller can win this
UPDATE jobs
   SET epoch  = epoch + 1,
       owner  = $target,
       status = 'restoring'
 WHERE id    = $job
   AND epoch = $current;
-- rows affected must be 1, otherwise abort and leave the source running

Why a heartbeat is not enough

A heartbeat answers "is it alive?" with a guess, several hundred milliseconds late. During the gap both nodes believe they own the job and both write. The epoch answers "who may write?" with a database predicate that is evaluated at commit time, on the only copy of the truth.

Every write carries the epoch

-- a step commit is rejected the moment ownership moves
UPDATE jobs
   SET seq = $next, state = $state, state_hash = $hash, updated_at = now()
 WHERE id = $job AND epoch = $epoch AND seq = $from
   AND status IN ('running','draining');
-- 0 rows  =>  the caller is stale  =>  stop, do not retry, do not write

The rejection is the proof. A fenced-out node does not have to "notice" anything, and the target does not have to wait for a timeout to expire before it is safe.

say this line on stage
"If both nodes could write, our demo would have shown double execution. It can't, because the second writer's WHERE clause no longer matches."

The subtle bug we found (and this is a good story to tell)

First version required status = 'running' in the commit predicate. That meant the moment the coordinator set draining, the source's in-flight step could no longer commit: the quiesce call hung and the migration timed out. Every migration would have silently lost one step — the exact failure the project exists to prevent.

Draining now means "start no new work", not "lose authority". There is a regression test specifically for it. On stage this costs 15 seconds and buys an enormous amount of credibility: it shows the team understands the difference between intent and authority.

07 / exactly-once and delta transfer

Two mechanisms that make the numbers real

1 · Exactly-once effects, structurally

Each step produces zero or more effects with stable IDs. The effect log and the state advance are written in one transaction, so they can never disagree:

BEGIN;
  INSERT INTO oplog (job_id, seq, epoch, op_id, result)
       VALUES ($job, $seq, $epoch, $op_id, $result)
  ON CONFLICT (job_id, seq, op_id) DO NOTHING;

  UPDATE jobs SET seq = $next, state = $state, ...
   WHERE id = $job AND epoch = $epoch AND seq = $from;   -- 0 rows => stale, abort
COMMIT;

If a step is ever executed twice — a restart, a retry, a resurrected source — the second insert is a no-op. Duplication stops being a policy and becomes a schema constraint.

Proof on stage: after a mid-flight migration, the op log has exactly N rows for N steps. The test asserts it; the dashboard shows it.

Why state shape matters (a good technical aside): the mutable counters must sit at the end of the serialised state and keep a fixed width. If a counter before a large blob changes length, every byte after it shifts, every chunk boundary moves, and dedupe collapses to zero. Our first version did exactly that and the metric was 0%. 08 / failure handling

What happens when the happy path breaks

This is the slide that separates a demo from a system. Every row below ends with exactly one authoritative owner.

FailureWhat the system doesWhat the audience sees
Source dies before the fence Coordinator rolls the status back and restarts the source from its committed state job continues on A
Source dies during checkpoint upload No checkpoint row exists, so nothing is restorable — the retry re-uploads. No partial state is ever adopted migration aborts
Target fails to restore (after the fence) Authority returns to the source with another epoch bump; the source restarts from the last checkpoint outcome: failed-failover-back
Both nodes alive, network partitioned Only the epoch holder can commit; the other gets a stale-epoch rejection and exits no duplicate execution
Restored state does not match the committed hash Target refuses to resume under the new epoch — blob and database disagree, so nothing runs hard stop, not a guess
Coordinator crashes mid-migration The epoch row still names one owner; a restarted coordinator can read where it stopped no split brain

Every attempt is recorded — including the failures

The migrations table stores from/to, epoch before and after, quiesce and restore timestamps, pause, bytes moved, chunks sent and skipped, and an outcome string: ok, aborted-quiesce-failed, aborted-fence-lost, failed-failover-back.

On stage, the valuable moment is showing a failed row and explaining what adjudicated it. Any team can show green rows; the red ones are the ones that prove the design.

honest gap — know it before a judge finds it
Failure handling exists inside a migration attempt. A node that dies while it owns a job and nobody asked it to migrate is not yet auto-recovered by a watchdog; the job stalls at running with a dead owner. One reaper loop (owner heartbeat + epoch bump to a survivor) closes it. If asked, say exactly that — it is a known, scoped gap, not an oversight.

14 / judge Q&A

Twelve questions you will get, and the answers

1 · "Is this just Kubernetes?" rehearse

No. Kubernetes reschedules a container; the process starts again from zero. We keep the workload's progress. A Kubernetes pod that is rescheduled is exactly the failure case we are designed to survive.

2 · "Why not CRIU / real process migration?" rehearse

Because it is all-or-nothing and environment-bound: root, kernel support, matching images, and checkpointing sockets and FDs. In a day it either works completely or you demo nothing, and it still cannot migrate arbitrarily. We chose the version that can be correct and measured. It is a deliberate scope boundary, written on the limitations slide.

3 · "What happens if the source never dies — just partitions?" rehearse

It becomes a fenced-out writer. Its next commit has WHERE epoch = 0, the row now says epoch = 1, zero rows are affected, and it stops with no side effects. Correctness does not depend on it noticing anything.

4 · "How is this exactly-once and not at-least-once?" rehearse

Because effects carry stable IDs and are inserted with ON CONFLICT DO NOTHING in the same transaction that advances the sequence number. A replay cannot re-apply an effect, and the state cannot advance without the effects. It's structural, not a policy.

5 · "Isn't this Temporal / durable execution?"

It is the same family, and we borrow the idea: persist progress at step boundaries. Temporal keeps the job pinned to a worker and replays history to recover. We physically relocate the running job to another machine and measure the move — that's the part they don't ship.

6 · "How big a state can you move?"

The demo moves ~12 KiB. The mechanism is size-agnostic — chunks are streamed through the object store — but we have not benchmarked large states, and pause grows with the delta size. Saying "we haven't measured beyond kilobytes" is the honest answer.

7 · "Is the coordinator a single point of failure?"

Yes, and it is the honest design boundary: the coordinator is stateless apart from its fleet registry, and the database holds all authority. A restarted coordinator reads the epoch and continues. Replicating the coordinator was deliberately out of scope for 24 hours.

8 · "What about non-idempotent side effects — an email, a payment?"

Either the effect is recorded through the op log (so it is applied once by construction), or the workload must be pure between checkpoints. We don't claim to make arbitrary side effects safe; we give you the log that makes them safe if you route them through it.

9 · "Why YugabyteDB and not Postgres?"

The fence is a distributed-systems primitive — ownership across machines — so putting it in a distributed SQL database is the coherent choice, and it survives the loss of a database node. The SQL is plain Postgres, which is why the same code runs on Postgres as an offline fallback.

10 · "What did the pause consist of?"

Checkpoint upload, the fence statement, the download and the hash verification. It excludes the current step, which is allowed to finish — that is why a 12 KiB state gives single-digit milliseconds on one machine.

11 · "What if the target rejects the restore?"

Authority returns to the source with another epoch bump, the source restarts from the last committed checkpoint, and the attempt is recorded as failed-failover-back. There is always exactly one owner, including during the failure.

12 · "What's the biggest thing missing?"

A watchdog. Today, failures during a migration are adjudicated correctly; a node that dies while owning a job with no migration in flight is not yet auto-recovered. It is a reaper loop, roughly two hours, and we would rather name it than hide it.

Glossary — if a judge uses one of these words

EpochA monotonic ownership counter. Whoever holds the current epoch may write; everyone else is stale.
FenceThe single guarded UPDATE that increments the epoch and moves ownership. Exactly one caller can win it.
QuiesceStop starting new work, finish the step in flight, checkpoint, then stop executing.
Op logAppend-only record of committed effects, keyed by (job, seq, op_id) so replays are no-ops.
CDCContent-defined chunking: chunk boundaries follow the data, so edits shift only nearby chunks.
ManifestThe checkpoint envelope: chunk list plus the hash the reassembled state must match.
DeltaThe bytes actually moved, which is the chunks the store does not already have.
PauseQuiesced → resumed interval. The headline number.
